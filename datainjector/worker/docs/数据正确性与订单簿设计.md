# 数据正确性与订单簿设计

## 1. 设计目标

- **统一入口**：对外只暴露 `integrity` handler，屏蔽内部乱序缓冲、缺失检测、幂等、阀门等细节。
- **抽象优先**：核心链路只解决“完整 × 顺序 × 幂等”三类问题，任何业务特殊性通过策略（Profile）外挂。
- **资源驱动**：回补调度（BackfillScheduler）可以直接选择资源（如 snapshot 通道、handler 前置 queue），灵活控制补数据注入位置。
- **与订单簿解耦**：订单簿组件只接受外部资源（diff / snapshot），状态管理与数据正确性彻底分离。

## 2. 组件划分

| 组件            | 职责                                                         |
|-----------------|--------------------------------------------------------------|
| `integrity.IntegrityHandler` | 配置解析、事件构建、串联序列引擎 / 幂等器 / 阀门 / 调度器 |
| `SequenceEngine` | 维护 expected seq、gap 探测、补数触发、快照确认             |
| `reorderBuffer` | 乱序缓存、顺序 drain、TTL / 容量回收                         |
| `deduper`       | 可选幂等过滤（message_id 或 stream+seq）                     |
| `Gate`          | 控制消息对下游可见时机，支持 snapshot hold / finality        |
| `Scheduler`     | 统一补数调度，按命令类型挑选目标（snapshot/diff/queue）      |
| `Orderbook.Engine` | 负责 ApplySnapshot / ApplyDiff，只处理领域状态             |

## 3. 事件与配置

### 3.1 统一事件 (Event)

- `Seq`：必填单调序列字段。
- `RangeStart`：范围覆盖起点（Binance Depth）。
- `StreamKey`：流标识，如 `symbol` 或 `chainId+topic`。
- `MessageID`：用于幂等的组合键。
- `Message`：原始 `types.Message`。

### 3.2 配置 (Config)

- `profile`：`generic` | `binance_depth` | `chain_blocks`（可扩展）。
- `keys`：`seq_field`、`range_start_field`、`stream_key_field`、`message_id_fields`。
- `sequence`：`eager_gap`、`max_range`、`max_delay`、`hard_timeout`、`max_gap`。
- `buffer`：`ttl`、`max_buckets`、`sweep_every`。
- `dedupe`：`enabled`、`ttl`。
- `gate`：`mode`（`none` / `snapshot_hold` / `finality`）、`finality_blocks`。
- `backfill`：`cooldown`、`options`（HTTP/WS/SDK 参数）。

Profile 会自动填充默认值，且允许业务按需覆盖。

## 4. 核心流程

1. **事件构建**：`integrity.IntegrityHandler` 从 metadata 提取 `seq/range/stream` 等字段，组装 Event。
2. **序列判断**：`SequenceEngine` 根据策略执行以下判断：
   - `seq == expected` → 即时放行。
   - `range` 覆盖 → 清理 buffer、推进 expected。
   - gap → 乱序缓存，并按阈值触发回补 / 跳跃。
3. **乱序缓冲**：`reorderBuffer` 维护 `seq -> []*Event` 执行顺序 drain、TTL/容量回收；被驱逐的序列会回补单点。
4. **回补调度**：
   - `Scheduler` 根据 `BackfillCmd.Type` 优先尝试 `snapshot` / `diff` / `queue` 等 target。
   - `ChannelTarget` 支持 Filter，可根据命令细分。
5. **幂等 & 阀门**：
   - `deduper` 基于 MessageID 或 `stream:seq` 做时间窗去重。
   - `Gate` 决定消息可见时机：`snapshot_hold` 在快照确认前缓存 diff，`finality` 缓存最近 N 块，默认直接透传。
6. **快照确认**：调用 `OnSnapshotApplied(lastSeq)` 后：
   - `SequenceEngine` 重置 `expected` 并释放 buffer；
   - `Gate` 同步 flush 缓存，保证 diff 在快照后一次性释放。

## 5. 订单簿协作模式

- 订单簿只依赖两个外部资源：`diff`、`snapshot`。
- `integrity` 保证送入订单簿的 diff 已满足顺序/完整/幂等，快照回补由 Gate 管理。
- `orderbook.Engine` 仅负责 ApplySnapshot/ApplyDiff，不再额外关心缺失检测。

## 6. 回补与资源管理

- `Scheduler.RegisterTarget(name, target)` 支持注册多种资源：
  - `snapshot`：快照通道；
  - `diff`：diff 通道；
  - `queue`：handler 前置队列或旁路注入；
  - `default`：向后兼容旧 channel。
- 调度策略：
  - `BackfillTypeSnapshot` → 优先 `snapshot`；
  - `BackfillTypeRange` → 优先 `diff` / `queue`；
  - 兜底遍历其他 target。
- `ChannelTarget` 可附加 Filter，自定义命令匹配逻辑。

## 7. 幂等策略

- 默认关闭，配置 `dedupe.enabled` 打开。
- 去重键：
  - 明确 `message_id_fields` → `field1|field2...`;
  - 若缺省，退化为 `stream:seq`。
- TTL 到期会自动清理历史 key。

## 8. 复杂度评估

- 底层复杂度来自多场景需求（乱序 / 范围覆盖 / 超时回补 / 快照 / 幂等 / 最终性），属于必要复杂度。
- 降复杂手段：
  1. **统一入口**：使用者只关心 `integrity` handler 与 profile 。
  2. **职责单一**：Sequence / Buffer / Dedupe / Gate / Scheduler 独立文件，便于测试与演进。
  3. **配置优先**：Profile 提供默认值，覆盖率>80%，剩余通过参数微调。

## 9. 监控与测试建议

- 指标：`expected_next`、buffer size、gap 次数、回补频率、跳跃次数、gate 缓存深度、幂等命中率。
- 日志：初始化、范围覆盖、回补命令、超时跳跃、sweep 驱逐、gate 放行。
- 单测：SequenceEngine（顺序/乱序/超时/跳跃/快照）、Gate、Scheduler 路由。
- 集成测试：构建 diff/snapshot 通道，验证补数据进入正确入口、快照后 diff 释放顺序正确。

## 10. 配置示例

### 10.1 Binance 深度

```yaml
- type: integrity
  profile: binance_depth
  sequence_field: final_update_id
  range_start_field: first_update_id
  stream_key_field: binance_symbol
  gate_mode: snapshot_hold
  backfill:
    http:
      enabled: true
      endpoint: https://fapi.binance.com/fapi/v1/depth
      query:
        symbol: BTCUSDT
        limit: 1000
```

### 10.2 区块流

```yaml
- type: integrity
  profile: chain_blocks
  sequence_field: height
  stream_key_field: chain_id
  gate_mode: finality
  finality_blocks: 12
  dedupe_enabled: true
  message_id_fields: ["hash"]
  backfill:
    ws:
      enabled: true
      endpoint: wss://xxx.example
```

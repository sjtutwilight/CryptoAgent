明确目标：先确定要演练的实时 ETL 故障场景（Kafka 积压、Flink checkpoint 压力、ClickHouse 写入飙升、单 token 倾斜等）。给每个场景写清楚目标到达速率、预期瓶颈、成功指标（延迟、吞吐、CPU/内存、ClickHouse QPS）。

MockDataProvider 扩展

增加全局 msg_rate（消息/秒）和突发模式（平稳 vs. 脉冲）的 CLI/环境参数。
支持按 token 配置：token_id、base_rate、burst_factor、burst_duration、空批概率等，用 YAML/JSON 管理场景。
提供可重复的随机种子及抖动开关，方便复现实验或模拟噪声流量。
场景库示例

积压压力：逐步提高总速率，直至 Kafka 分区带宽/磁盘 80%，用 Kafka lag + Flink watermark 观察积压。
热点倾斜：70% 流量集中在单一 token，20% 分布在 5 个 token，其余背景噪声，观测 Flink key-group 不均衡并尝试重分区、rebalance 或 keyed state 调优。
突发事件：低基线 + 周期性 10× 爆发（30–60s），检验 checkpoint、ClickHouse 批量刷新行为。
慢生产者 / 空闲分区：故意将一半分区速率降到接近 0，确认 Flink 空闲检测生效且指标仍准确。
Schema 漂移：间歇发出带可选字段或损坏 payload 的消息，验证 DLQ/毒丸处理。
演练手册

每个场景都记录：mock 配置、启动命令（如 ./mockDataProvider --scenario skew-hotspot --msg-rate 50k）、关键 Flink/Kafka/ClickHouse 指标、调优步骤（增并行度、调 Kafka fetch、改 ClickHouse 批量等）。
自动化流程：compose 起基础设施 → 部署 Flink job → 启动 mock → 用 Kafka UI / Flink UI / ClickHouse 系统表监控 → 释放资源。
保存调优前后的仪表盘或指标快照（lag、CPU、RocksDB 状态、ClickHouse 插入速率），积累直觉。
监控与告警：Mock 侧暴露 Prometheus 指标（每 token 速率、丢弃数）；消费侧重点关注 Kafka lag、Flink checkpoint 时长/失败、算子忙闲、ClickHouse 插入延迟。根据场景设置阈值，便于判断调优是否成功。

调优实验：场景运行中迭代调整 Kafka 分区/保留、Flink 并行度/ checkpoint 间隔/背压参数、ClickHouse 批量大小与去重策略，并记录指标变化，形成适用于生产的调优手册。

复盘模板：每次演练后写简短复盘：触发场景、观察到的问题、指标表现、调优动作、剩余风险。不断积累即可在真实事故中快速复制经验。

通过以上流程，就能利用 mockDataProvider 精确控制总速率或单 token 速率，系统演练 Kafka → Flink → ClickHouse 在倾斜、积压、突发压力下的微调与应对。

## 阶段 1：指标体系与 SLO 落地

## 阶段 2：日志与追踪体系升级

- **目标**：将关键路径端到端 trace 化，日志结构化并可与指标联动，实现分钟级根因定位。
- **范围与任务**：
  - 统一日志规范：JSON 格式、必填字段（traceId/spanId/token_id/request_id）、日志级别、保留策略。
  - Promtail + Loki 调整：多环境区分、索引标签控制成本、采样策略。
  - 引入 OpenTelemetry（SDK + Collector）：Injector/Flink/ClickHouse API/前端 端到端传递 context；Flink operator 中注入 span，ClickHouse 写入增加 trace 注解。
  - 建立“指标 ↔ 日志 ↔ Trace”跳转：Grafana 面板点击即可钻取 Loki/Tempo。
  - 为典型故障（Kafka 积压、慢写、API 延迟）编写 Trace 分析 Runbook。
- **产出**：
  1. 日志规范文档与 lint/CI 校验（如 log schema 校验脚本）。
  2. OTel Collector 配置 + 各服务集成 PR。
  3. Trace Dashboard（拓扑视图、链路延迟分布）。
- **验收**：从前端请求到 ClickHouse 写入的 trace 可在 30 秒内检索；任一 P1 告警可在仪表盘中一键跳转对应日志和 trace。
- **落地模板**：
  - 日志 Schema（YAML/JSON）示例：
    ```yaml
    log_schema:
      level: enum(INFO, WARN, ERROR)
      timestamp: iso8601
      service: string
      component: string
      trace_id: string
      span_id: string
      token_id: string
      request_id: string
      message: string
      extra: object
    ```
  - Promtail/Loki 配置片段模板：包含多环境 `pipeline_stages`、采样率、动态标签白名单。
  - OpenTelemetry 集成步骤清单：依赖/SDK → Trace context 传递 → 关键 span 列表（Injector 请求、Flink Source/Operator、ClickHouse Insert、API Handler、前端请求）→ 采样策略（99% for P1 事务，其余 10%）→ Collector pipeline（otlp → tempo + logging）。
  - Trace Runbook 模板：告警入口 → 指标定位 → Trace 检索语句 → 关键 span 检查点 → 常见原因 → 处置动作。

## 阶段 3：告警体系与自愈手册

- **目标**：将阶段 1/2 的指标与 trace 转化为可靠的告警与处置流程，实现高优先级事件的闭环。
- **范围与任务**：
  - 定义告警等级（P1~P3）及响应 SLA，梳理通知路径（短信、IM、值班系统）。
  - 基于 SLO/SLI 制定 Alertmanager 规则：Kafka lag、Flink checkpoint 失败、ClickHouse Merge backlog、API 95 延迟、前端错误率、MockDataProvider 丢弃率等。
  - 编写自动诊断脚本：例如 `scripts/diag_kafka_lag.sh` 自动查询 partition lag、消费速率、Flink 后压状态。
  - 建立自愈动作：重启策略、弹性扩缩（Flink 并行度、ClickHouse shard）、流量切分或降级。
  - Runbook 规范化，定义触发条件、检查项、操作步骤、回退策略。
- **产出**：
  1. 告警规则库（alert_rules.yml）+ Alertmanager 路由配置。
  2. 自愈脚本与 README 说明。
  3. Runbook 仓库（docs/runbooks/*.md），覆盖至少 10 个高频场景。
- **验收**：任一 P1 告警 5 分钟内路由给值班；90% 告警在 Runbook 范围内有明确操作；自愈脚本可在演练中成功执行。
- **落地模板**：
  - 告警定义表：

    | 告警名称 | 触发条件 | 严重级别 | 通知渠道 | Runbook | 自愈脚本 | Owner |
    | --- | --- | --- | --- | --- | --- | --- |

  - Alertmanager 路由示例：按 `severity`, `service`, `region` 组合路由。
  - 自愈脚本框架（bash/python）：支持 dry-run、日志、Prometheus API 查询。
  - Runbook 模板：告警说明 → 影响范围 → 立即动作 → 诊断列表 → 修复步骤 → 验证 → 后续跟进。

## 阶段 4：演练自动化与指标留存

- **目标**：可一键复现多种故障场景，自动采集指标/日志/trace，输出标准化复盘。
- **范围与任务**：
  - 对照“MockDataProvider 扩展”章节，将场景定义抽象为 YAML（速率、token 分布、突发参数、schema 漂移概率）。
  - 编写 Makefile/脚本：`make drill scenario=skew-hotspot` 自动执行 compose 启动 → 部署 Flink job → 加载场景 → 采集指标。
  - 接入 Prometheus API / Grafana Snapshot / Loki 导出，保存演练期间的关键指标与日志到 `observability/drills/<date>`。
  - 自动生成复盘模板（Markdown）：包含场景、指标曲线、告警触发、自愈动作、结论。
  - 将演练脚本纳入 CI 定期运行（可选夜间/周末），验证告警和自愈链路。
- **产出**：
  1. `observability/drills/` 目录：场景定义、脚本、结果存档。
  2. Grafana Snapshot/ClickHouse 系统表导出存档。
  3. 复盘报告库，便于知识沉淀。
- **验收**：演练命令 15 分钟内完成并生成报告；指标/日志/trace 可追溯；演练中所有关键告警均成功触发且 Runbook 生效。
- **落地模板**：
  - 场景定义示例（YAML）：
    ```yaml
    scenario: skew-hotspot
    description: 70% 流量集中单 token
    msg_rate: 50000
    tokens:
      - token_id: HOT
        base_rate: 35000
      - token_id: OTHER
        base_rate: 5000
    burst:
      enabled: false
    schema_drift:
      enabled: true
      probability: 0.05
    ```
  - Drill Pipeline：`setup`→`deploy-jobs`→`run-mock`→`collect`→`teardown`→`report`。
  - 复盘模板字段：`事件编号`、`场景`、`开始/结束时间`、`告警`、`指标快照`、`调优动作`、`剩余风险`。

## 阶段 5：治理、推广与持续优化

- **目标**：让可观测能力成为项目默认能力，通过规范、模版、评审与度量保证持续演进。

## Context

当前 `role.Manager.Apply` 采用 `stopAll -> startRole*` 的串行流程，导致热更新存在全局中断窗口；且中途启动失败时会停留在“旧角色已停、新角色仅部分启动”的不一致状态。该行为与生产场景对连续采集和数据完整性的要求冲突。

本次仅覆盖 P0：保证热更新过程对非目标角色无扰动，目标角色切换失败可回滚，避免全局中断与半成功状态；不引入灰度发布、分批调度、跨实例编排。

## Goals / Non-Goals

**Goals:**
- 将角色热更新改为按 `role_id` 的增量 reconcile，而非全量替换。
- 在单次 apply 内实现“先准备、后提交”的两阶段切换。
- 确保单角色切换失败时仅影响该角色，其他角色持续运行。
- 提供按角色的 apply 结果，支持控制面重试失败项。

**Non-Goals:**
- 不实现多 worker 的分布式一致性切换。
- 不实现自动灰度、金丝雀或批次编排策略。
- 不改造 role 内部业务 handler/sink 语义，仅调整生命周期管理与控制面回执。

## Decisions

### 决策 1：Apply 改为 Reconcile（按 role 差异执行）
- 方案：计算 `add/update/remove/unchanged`，仅操作差异角色。
- 原因：从根源消除 `stopAll` 带来的全局扰动。
- 备选：保留全量替换但增加失败恢复。
- 放弃原因：即便可恢复，也仍存在全局停机窗口，无法满足 P0。

### 决策 2：两阶段切换（Prepare/Commit）
- 方案：
  - Prepare：对 `add/update` 全量执行 build + validate + readiness check，失败即整体拒绝提交。
  - Commit：逐角色 swap，新实例就位后再停止旧实例。
- 原因：将“构建失败”与“线上切换”隔离，避免运行中态被污染。
- 备选：边构建边替换。
- 放弃原因：一旦中途失败无法保证一致性。

### 决策 3：按角色回滚而非全局回滚
- 方案：Commit 中单角色失败时回滚该角色到旧 runner，记录失败并继续处理其他角色。
- 原因：最小化故障域，满足“一个 role 失败不影响其他 role”的核心诉求。
- 备选：任何失败即整批回滚。
- 放弃原因：实现复杂度更高且会扩大故障影响面，不符合 P0 快速收敛目标。

### 决策 4：Apply 串行化 + 生命周期超时保护
- 方案：增加 `applyMu` 串行化 apply 操作；stop/wait 增加超时上限。
- 原因：避免 `Apply` 与 `Stop` 并发导致竞态或永久阻塞。
- 备选：乐观并发 + CAS。
- 放弃原因：当前代码结构以互斥 map 为主，串行化更稳健且改动小。

### 决策 5：控制面返回按角色结果
- 方案：`/api/roles/apply` 返回 `results[]`（role_id、action、status、error）。
- 原因：支持精确重试与故障定位。
- 备选：继续只返回全局 `ok/error`。
- 放弃原因：无法支撑部分成功场景下的运维动作。

## Risks / Trade-offs

- [风险] 两阶段准备会增加一次性构建开销与切换时延。  
  [缓解] 仅对差异角色执行 prepare，并记录阶段耗时指标。

- [风险] 引入 readiness 判断后，部分 role 可能长期处于未就绪。  
  [缓解] 提供超时与失败原因回传，默认回退到旧实例。

- [风险] 逐角色提交导致短时间内新旧实例并存。  
  [缓解] 提交顺序固定且旧实例在新实例就绪后立即优雅停止，控制并存窗口。

## Migration Plan

1. 增加新管理流程与数据结构（diff 结果、prepare 缓存、per-role result）。
2. 将 `Apply` 改为 `resolve -> prepare -> commit`，移除流程内 `stopAll`。
3. 调整 API 返回结构，保持旧字段兼容一个过渡版本（如 `status` 继续保留）。
4. 增加回归测试：
   - 更新集合中某角色构建失败时，其他在线角色不中断；
   - 单角色切换失败触发回滚，旧实例继续运行；
   - remove 仅影响目标角色。
5. 灰度上线后观察错误率与切换耗时，再移除旧兼容分支。

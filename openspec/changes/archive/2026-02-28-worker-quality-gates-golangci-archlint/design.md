## Context

`datainjector/worker` 代码规模已超过 2 万行，且存在超大文件与职责边界漂移，当前缺少稳定的自动化质量门禁。团队需要一个“低侵入、可脚本化、可渐进收敛”的方案，在不引入常驻组件的前提下，为后续架构优化提供持续反馈。

约束如下：
- 工具必须是命令行方式执行，支持本地与 CI 复用。
- 首期仅落地 `golangci-lint` 与 `go-arch-lint`，避免范围膨胀。
- 对历史存量问题采用渐进收敛，优先阻断新增违规。

## Goals / Non-Goals

**Goals:**
- 建立 worker 模块统一质量门禁入口，覆盖静态代码质量和包依赖架构规则。
- 输出机器可读结果（如 JSON）供 Codex 与 CI 使用。
- 约束新增架构违规，降低重构回归风险。

**Non-Goals:**
- 不在本次引入常驻服务（如 SonarQube Server）。
- 不在本次一次性清理全部历史 lint/架构债务。
- 不在本次扩展到 `datainjector/worker` 之外的其他模块。

## Decisions

### 决策 1：使用双工具最小组合（golangci-lint + go-arch-lint）
- 方案：首期只启用两个 CLI 工具，分别负责代码质量与架构边界。
- 理由：覆盖面和复杂度平衡最佳，接入成本低，能够快速形成可执行门禁。
- 备选方案：
  - 仅用 `golangci-lint`：无法表达跨包架构约束，不能防止边界漂移。
  - 增加 `Semgrep`：收益高但规则建设成本更大，放到下一阶段。

### 决策 2：统一单入口脚本执行质量检查
- 方案：提供单一执行入口（如 `tools/quality_gate.sh`），内部顺序执行两类检查。
- 理由：减少使用心智负担，确保本地与 CI 行为一致。
- 备选方案：分别手动执行两条命令，易出现漏跑与参数漂移。

### 决策 3：历史债务采用基线冻结，新增违规阻断
- 方案：对首期发现的存量问题生成基线，CI 阻断“新增违规”。
- 理由：避免一次性清债阻塞交付，先建立制度再持续收敛。
- 备选方案：一次性零违规门禁，短期不可落地且高概率回滚。

### 决策 4：架构规则按核心数据链路定义允许依赖
- 方案：明确 `role -> emitter/caller/handler/sink -> protocol/resource/util` 的依赖方向；禁止反向依赖与横向越层。
- 理由：与现有模块职责匹配，能直接约束已识别问题（如 handler 与 caller 互相穿透）。
- 备选方案：仅做文档约定，不具备自动校验能力，容易失效。

## Risks / Trade-offs

- [规则过严导致开发体验下降] → 先启用核心规则并允许小范围豁免，按迭代逐步收紧。
- [历史债务过多影响首次接入] → 使用基线冻结策略，只阻断新增问题。
- [架构规则误伤合法依赖] → 首轮以观测模式验证 1~2 周，再切换强阻断。
- [工具版本漂移导致结果不一致] → 固定版本并在文档中声明安装方式与最低版本。

## Migration Plan

1. 在 `datainjector/worker` 增加 `golangci` 配置与 `go-arch-lint` 配置。
2. 新增统一执行脚本，支持本地与 CI 一致调用。
3. 在本地生成首次检查结果，建立历史问题基线。
4. 将 CI 切换到“新增违规阻断”模式。
5. 观察稳定后逐步提高阈值与规则覆盖。

## Open Questions

- 基线文件是否提交到仓库，还是由 CI 工件托管。
- 首期阻断策略是否按分支区分（主干强阻断、功能分支告警）。
- `golangci-lint` 首批启用规则清单是否需要按包分级（integrity/role 更严格）。

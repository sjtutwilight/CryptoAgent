## Context

`datainjector/worker` 在 spot WS 链路上出现高频协议读错，当前虽然具备“报错即重连”能力，但缺少重连节流、冷静期和订阅恢复幂等控制，导致重连抖动环。与此同时，`ws.buffer.drop` 高发说明消费链路存在持续背压，进一步放大缺口检测和 backfill 触发频率。目标是在现有架构内做增量加固，不引入新服务或跨项目改造。

## Goals / Non-Goals

**Goals:**
- 将 WS 重连行为从“立即重试”改为“受控重试”，显著降低重连风暴。
- 确保重连后的订阅恢复幂等，避免重复订阅触发上游限流。
- 为 backfill 失败建立有限重试与状态闭环，阻断无限抖动重试。
- 通过背压治理降低 `ws.buffer.drop`，减少假缺口与连锁补数。
- 建立可观测与告警基线，可区分链路问题、限流问题和消费瓶颈。

**Non-Goals:**
- 不引入 IP 切换或代理池策略。
- 不重构为全新流式框架或引入新的消息中间件。
- 不改变业务数据语义，仅提升可靠性和稳定性。

## Decisions

### 1) 采用“重连控制器”统一管理重连节奏
- 决策：在现有 websocket 管理层增加重连控制器，提供指数退避+jitter、最小重连间隔、单飞重连、1008 冷静期。
- 原因：快速止血且改动集中，能显著降低重连风暴与限流反馈回路。
- 备选方案：
  - 仅保留现有指数退避：无法抑制实例内并发重连与同频重试。
  - 引入独立熔断服务：改造面过大，不符合“不过度设计”。

### 2) 订阅恢复采用“期望集 + 差量恢复”
- 决策：维护 `desired_subscriptions`，重连成功后按差量恢复，仅发送一次；短窗对相同 stream 去重。
- 原因：避免重复订阅触发风控，同时兼容现有订阅调用点。
- 备选方案：每次重连全量重发；实现简单但最易触发限流。

### 3) 同 endpoint 合并连接
- 决策：按 endpoint 复用连接，在单连接中承载 `depth + aggTrade` 等多 stream。
- 原因：减少连接数和握手开销，降低被策略限流概率。
- 备选方案：维持每 role 一连接；隔离性好但连接压力和限流风险更高。

### 4) backfill 失败闭环
- 决策：backfill 采用有限重试 + 退避 + 耗尽状态回写（degraded）+ 冷静期再尝试。
- 原因：阻断无限重试导致的 CPU/IO 抖动，避免将失败持续放大。
- 备选方案：失败立即重试到底；会持续放大故障。

### 5) 背压治理优先于“补数增量”
- 决策：增加队列水位、有限并发消费、批量 sink，必要时触发降级保护与显式丢弃计数。
- 原因：消费端不稳会持续制造假缺口，先稳吞吐再谈补数可靠性。
- 备选方案：仅增加 backfill 频率；会掩盖根因并加剧抖动。

### 6) 指标与告警标准化
- 决策：统一输出 `ws.reconnect.start/success`、`ws.buffer.drop`、`backfill.exhausted`、`ws.policy.1008`，并配置阈值告警。
- 原因：需要在运行时快速判断故障主因，缩短定位时间。

## Risks / Trade-offs

- [重连等待时间变长] → 通过冷静期与退避参数分层配置（spot/perp 分开），并保留紧急覆盖配置。
- [合并连接后单连接影响面增大] → 通过 endpoint 级隔离与独立健康状态，避免全链路联动失败。
- [背压策略引入可控丢弃] → 对丢弃量强制上报并告警，触发自动降级和人工介入。
- [新增状态机复杂度] → 状态转换最小化，仅保留 `healthy/degraded/cooldown` 三态并写入统一日志。

## Migration Plan

1. 部署新 `worker-app` 二进制，确认移除旧 backfill 路径（先消除 404 干扰）。
2. 灰度开启重连控制器（仅 spot），观察 30 分钟指标。
3. 开启订阅幂等与 endpoint 连接合并。
4. 开启 backfill 失败闭环与背压治理参数。
5. 启用告警阈值并完成值班手册更新。

回滚策略：所有新增能力均由配置开关控制；出现异常可逐项关闭（先关连接合并，再关背压策略，最后回退重连控制器）。

## Open Questions

- 不同 endpoint 的默认冷静期参数是否分层（例如 fstream 与 stream）？
- `ws.buffer.drop` 的告警阈值按绝对值还是按速率（每分钟）更合适？
- backfill 耗尽后自动恢复窗口是固定值还是指数扩展？

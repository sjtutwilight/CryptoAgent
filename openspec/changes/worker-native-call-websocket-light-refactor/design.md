## Context

当前 `datainjector/worker/internal/caller/native_call_websocket.go` 集中承载了 WebSocket caller 的主要逻辑：初始化配置、订阅构造、多协议消息处理、共享路由、缓冲与背压、RPC pending 匹配。文件体量和职责密度持续上升，导致定位问题、评审和并行开发成本明显增加。

当前实现还存在隐患累积风险：共享状态读写边界不够清晰、拆分与治理若分离会造成重复改动与验证窗口拉长。本次改动目标是在同一 change 内完成“轻量重构 + 隐患治理”，并通过分阶段执行控制风险。

## Goals / Non-Goals

**Goals:**
- 将 WebSocket caller 代码按职责拆分为更小的实现单元，降低单点复杂度。
- 保持行为等价：保持现有调用入口、消息路由语义、元数据字段和错误处理策略。
- 同步治理已识别隐患：收敛并发状态边界与共享路由一致性风险。
- 保持运维与测试连续性：现有测试可继续覆盖关键路径，并补充必要回归与并发用例。

**Non-Goals:**
- 不新增协议类型，不扩展新的业务能力。
- 不调整公开配置结构与字段命名。
- 不引入新的外部依赖或重写底层 websocket protocol 层。

## Decisions

1. 采用“按职责拆文件”的最小改造路线
- 决策：将配置解析、消息处理、订阅路由/共享连接、缓冲回压逻辑拆分为独立文件，`WebSocketCall` 结构与入口方法保持稳定。
- 备选：大规模重构为多层接口/插件体系。
- 取舍：当前优先降低风险并保留可回滚性，因此选择轻量拆分。

2. 保持行为优先级高于结构完美
- 决策：在实现中禁止协议语义变更，保持现有 `jsonrpc/binance/hyperliquid` 的分发与 metadata 行为一致。
- 备选：借重构同步统一三类协议处理模型。
- 取舍：统一模型收益较大但风险更高，后续独立 change 再做。

3. 在同一 change 内分阶段完成治理
- 决策：阶段一先做零行为变更重构；阶段二针对并发/路由明显隐患进行治理；阶段三完成回归与并发验证。
- 备选：先重构再开新 change 治理。
- 取舍：分开 change 会产生重复变更与双重回归成本，因此在同 change 内分步推进。

4. 以测试护栏约束重构与治理风险
- 决策：保留并补充 caller 目录下 websocket 路由/缓冲/共享相关测试，并增加并发检查，确保重构与治理后的关键路径一致。
- 备选：仅依赖人工 review。
- 取舍：该文件含并发状态机与路由逻辑，必须由自动化测试兜底。

## Risks / Trade-offs

- [Risk] 拆分后跨文件调用增多，定位时需要跳转更多文件。
  - Mitigation: 通过明确命名和文件职责边界降低跳转成本。
- [Risk] 共享连接与订阅路由状态若拆分不当可能引入竞态。
  - Mitigation: 明确锁保护边界，并通过现有 routing/backpressure 测试验证。
- [Risk] 治理步骤可能在收敛锁边界时引入行为偏差。
  - Mitigation: 严格执行“先重构后治理”的分步提交，并在每步后执行回归测试。
- [Risk] 轻量重构无法一次性解决所有历史复杂性。
  - Mitigation: 本次先完成明显隐患收敛，剩余优化在后续 change 渐进推进。

## Migration Plan

1. 阶段一：在 `caller` 目录完成函数搬迁与职责拆分，保持外部调用点不变。
2. 阶段二：在同一分支完成明显隐患治理，收敛并发状态访问和路由状态同步边界。
3. 阶段三：运行 websocket caller 相关回归与并发检查，确认路由、缓冲与 RPC 路径行为一致。
4. 若出现行为偏差，优先回退到上一步稳定提交，再做局部修正。

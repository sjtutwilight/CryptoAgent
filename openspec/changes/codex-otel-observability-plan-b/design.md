## Context

当前仓库已有 Prometheus + Loki + Grafana 的可观测底座，并在数据平台侧预留了 trace 关联位，但 Codex 行为尚未接入统一观测链路，导致以下问题长期无法量化：

1. 高频重复操作无法自动识别为脚本化候选。
2. 低价值读取（读很多、改很少、测很少）难以被系统发现与治理。
3. 工具调用失败与决策链退化只能靠人工复盘，缺少持续追踪。

本次方案 B 的核心是把 Codex OTel 行为数据与现有观测体系打通，并建立“采集 -> 分析 -> 建议 -> 验证”的闭环，以可量化数据驱动后续提效动作。

## Goals / Non-Goals

**Goals:**
- 打通 Codex OTel 端到端链路，确保日志与 trace 可检索、可关联。
- 建立决策链效率指标体系（重复步骤、低效读取、失败热点、首次产出时延）。
- 建立优化建议闭环（脚本候选、文档候选、执行后效果验证）。
- 采用可观测优先策略，完整保留提示词上下文以提升归因与优化准确性。

**Non-Goals:**
- 不在本次变更中改造 Codex 内部推理策略或模型行为。
- 不在本次变更中自动执行“无人审核”的代码改造。
- 不将全部历史日志回填为新指标，仅从接入后增量生效。

## Decisions

### Decision 1: 采用 `Codex -> OTel Collector -> Loki/Tempo/Grafana` 的增量接入拓扑
- 决策：新增 OTel Collector 与 Tempo（trace 后端），Collector 负责接收 OTLP、统一处理后分别输出到 Loki 与 Tempo。
- 原因：与当前 Observability 栈兼容性最好，可最小改动接入 trace 能力。
- 备选方案：
  - Codex 直连 Loki/Tempo：缺少统一治理层，后续采样/路由/权限控制不易演进。
  - 先只做日志不做 trace：无法分析完整决策链，后续返工成本高。

### Decision 2: 采集策略采用“可观测优先”，开启原始用户提示词
- 决策：Codex 侧启用 `log_user_prompt=true`，Collector 不执行关键字段内容级脱敏，保留原始上下文以最大化分析信号。
- 原因：决策链优化依赖完整上下文，字段脱敏会破坏关键归因线索与模式识别准确性。
- 备选方案：
  - 最小化采集（禁用 prompt）：安全边界更保守，但无法满足“可观测优先”目标。
  - 全量采集 + 字段脱敏：可降低明文暴露风险，但会损失部分分析可解释性。

### Decision 3: 建立统一事件字段契约，优先可分析性而非“全量原始数据”
- 决策：定义必填维度：`environment/service.name/session_id/event.name/outcome/repo/workspace`，并为 tool/patch 事件补充标准字段。
- 原因：保证跨会话、跨仓库可聚合分析，避免后续口径分裂。
- 备选方案：
  - 仅依赖原始事件：字段不稳定，难以构建稳定指标与告警。

### Decision 4: 决策效率分析采用“日批 + 轻量规则引擎”先行
- 决策：新增每日分析任务，按固定窗口生成 `重复步骤候选 / 文档约束候选 / 工具失败热点` 报告，不立即引入复杂在线学习系统。
- 原因：先建立稳定可解释闭环，控制实施复杂度。
- 备选方案：
  - 实时流式推荐：实时性高，但需要更重的状态管理与误报治理。

### Decision 5: 建议输出采用“人工审核门禁 + 效果回归验证”
- 决策：建议项必须经过人工审核后才能进入脚本/文档落地，并在落地后按统一指标做前后对比。
- 原因：避免错误自动化扩大影响，保证优化动作可追责、可回滚。
- 备选方案：
  - 全自动落地：效率高但风险不可控，不适合首期上线。

## Risks / Trade-offs

- [风险] OTel 事件量上升导致 Loki/Tempo 存储与查询压力增大  
  -> Mitigation: Collector 侧启用采样、批处理与保留策略分级，先按关键事件集上线。

- [风险] 字段规范不一致导致分析口径漂移  
  -> Mitigation: 在规范中固化必填字段与校验规则，并增加事件契约检查。

- [风险] 分析建议误报影响团队信任  
  -> Mitigation: 报告附带证据链（事件样本、计数、趋势），人工审核后再执行。

- [风险] 过度采集引发安全顾虑  
  -> Mitigation: 强化访问控制、最小权限、审计日志与保留时长分级，不通过脱敏降低信号质量。

## Migration Plan

1. 在编排中新增 OTel Collector 与 Tempo，并打通 Grafana 数据源。
2. 配置 Codex OTel 导出到 Collector，先在测试环境验证事件完整性与稳定性。
3. 上线 Codex 行为看板与告警（错误率、失败热点、长时无产出会话）。
4. 上线每日分析任务，输出优化建议清单（脚本候选、文档候选、失败热点）。
5. 建立评审与落地流程：审核建议 -> 脚本/文档改造 -> 指标回归验证。
6. 生产灰度与回滚：
   - 回滚优先级：先停分析任务 -> 再停 Collector 路由 -> 最后停 Codex OTel 导出；
   - 保持业务链路不受影响，确保关闭观测后 Codex 仍可正常执行。
